# 브랜치 운영 규칙

이 레포는 "무엇이 공휴일인가"를 근거와 함께 들고 있는 것이 목적이다.
브랜치와 커밋의 모양도 그 목적에 맞춘다 — 나중에 어느 값이 어디서 왔는지
되짚을 수 있어야 한다.

`CLAUDE.md` 와 `AGENTS.md` 에 압축본이 실려 있다. 정본은 이 파일이다.

## 브랜치 이름

접두사 4종만 쓴다.

| 접두사  | 쓰는 자리 |
|---------|-----------|
| `feat/` | 기능 추가 |
| `fix/`  | 버그 수정 |
| `docs/` | 문서만 |
| `data/` | YAML 데이터 변경 (`sources/`, `rules/*/*.yaml`) |

이슈 번호는 브랜치 이름에 넣지 않는다. 필요하면 PR 본문에 `Closes #N` 을 적는다.

브랜치 이름은 임시 레이블이고 이슈 번호는 영구 식별자다. 둘을 붙이면 이름만
보고는 무엇을 하는 브랜치인지 알 수 없고(`fix/123` 은 아무것도 말하지 않는다),
번호는 어차피 PR 이 들고 있다.

## 한 브랜치 = 한 기능

`holiday_01` 의 `feat/kr-holiday-calendar` 에는 6 개 기능이 한 브랜치에 들어
있었다. 초기 구축이라 예외로 인정한다. 앞으로는 쪼갠다.

판단 기준은 하나다.

> **"이 브랜치만 되돌리면 무엇이 사라지는가"에 한 문장으로 답할 수 없으면 쪼갠다.**

답이 "음력 변환과 대체공휴일 유도와 .ics 직렬화가 사라진다"라면 그건 세
브랜치다. `git revert` 를 할 수 없는 브랜치는 되돌릴 수 없는 브랜치다.

## PR 필수

`data/` 를 포함해 **모든** 브랜치는 PR 을 거친다. `main` 에 직접 푸시하지 않는다.

**긴급 예외를 두지 않는다.** 임시공휴일 발표가 임박해도 PR 을 만든다.
발행은 `workflow_dispatch` 로 즉시 돌릴 수 있으므로(`.github/workflows/publish.yml`)
PR 이 병목이 되지 않는다. 급한 것은 발행이지 병합이 아니다.

**GitHub 브랜치 보호 규칙은 걸지 않는다.** 1 인 레포에서 보호 규칙은 지킴이가
아니라 자기 우회 절차만 늘린다 — 급할 때 규칙을 끄고 푸시한 뒤 다시 켜는
습관이 생기고, 그 습관이 생긴 시점부터 규칙은 아무것도 막지 못한다.

규칙을 지켰는지는 git 히스토리에 남는 것으로 족하다. 직푸시한 커밋은 히스토리에
그대로 보인다. 그것이 기록이자 제재다.

## merge commit 고정

병합은 **merge commit** 으로 한다. **squash 금지.**

개별 커밋의 근거를 보존하는 것이 이 레포의 목적이다. squash 는 그것을 정확히
반대로 한다 — 열 개 커밋의 커밋 메시지 열 개가 하나로 뭉개지고, 나중에
`git log` 나 `git blame` 으로 "이 줄은 왜 이렇게 됐나"를 물으면 브랜치 전체를
뭉친 요약 하나만 나온다.

데이터 변경에서 특히 그렇다. 한 브랜치에 임시공휴일 세 건을 넣었다면 각각
다른 관보에 근거한 세 커밋이어야 하고, 그 대응이 유지되어야 나중에 한 건만
정정할 수 있다.

## 데이터 변경 커밋

`data/` 브랜치의 커밋 메시지에는 근거를 적는다. 관보 호수 / 고시 번호 /
국무회의 일자 중 **확인된 것**을 적는다. 확인하지 않은 것을 적지 않는다.

이것은 CI 로 강제하지 않는다. 커밋 메시지 검사는 형식만 통과시키고 내용은
보지 못한다 — "관보 제20000호" 라고 적혀 있어도 그 호수가 맞는지 CI 는 모른다.
형식 검사를 통과했다는 사실이 근거를 확인했다는 인상을 주면 오히려 나쁘다.

**강제되는 것은 YAML 의 `source` 필드다.** `tests/test_designated_sources.py` 가
`rules/kr/designated_holidays.yaml` 의 모든 항목에 `source` 가 있는지 검사한다.

### 근거의 정본은 커밋 메시지가 아니라 YAML 의 `source` 다

두 가지 이유다.

1. 파일을 열면 바로 보인다. 커밋 메시지는 그 값이 언제 들어왔는지 알아야
   찾을 수 있고, 값이 여러 번 고쳐졌으면 어느 커밋이 현재 근거인지 다시 따져야 한다.
2. **피드의 `DESCRIPTION` 으로 그대로 흘러간다.** `rules/kr/feed.py` 의
   `_designated_description()` 이 이 필드를 읽어 구독자 캘린더에 내보낸다.
   즉 `source` 는 내부 메모가 아니라 발행물의 일부다.

커밋 메시지의 근거는 그 변경이 **왜 그때 들어왔는지**를 남기는 것이고,
`source` 는 그 값이 **지금 무엇에 근거하는지**를 남기는 것이다. 역할이 다르므로
둘 다 적되, 어긋나면 `source` 가 맞다.
