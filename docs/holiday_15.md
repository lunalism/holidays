## 1. 정정

- **publish cron 발화일은 UTC 기준 일·화·목이다.** `23 21 * * 0,2,4` 의
  요일 필드는 UTC 요일이고, KST 수령일이 월·수·금이다. 세션 중 KST 요일을
  UTC 날짜에 그대로 붙여 2026-09-09(수) 예정분을 조사했으나 그 날짜는
  발화 대상이 아니었다 — 지연이 아니라 예약 없음. **관측은 1/6 에 머문다.**
  남은 관측 일정(UTC): 09-13 · 09-15 · 09-17 · 09-20.
- **de 계열 verified false 는 xfail 로 다루지 않는다.** #62 프롬프트가
  "false 항목이 들어오니 xfail 델타가 정상"을 전제했으나, 레포 실태는
  자동 xfail 이 kr fixture 전용이고 de 의 false 는 source_todo + 상태
  고정 테스트다(HH 가 이미 그 방식). 프롬프트의 선행 실측 조항이 오류를
  흡수해 결과는 무사했다. 이 세션 xfailed 4 · xpassed 29 불변.
- **결속 테스트는 추가 직후 빨개지지 않는다.** #59 프롬프트가 "테스트
  선행 → red 확인"을 전제했으나, 결속은 존재하는 줄만 검사하므로 아직
  없는 넷은 잡을 수 없다. 그 시점 빨간 것은 목록 일치 두 건이었다
  (2 failed, 8 passed). 안전망 선행의 목적(변경 전 계약 고정)은 그대로
  달성됐고 전제만 좁았다.
- **레포 밖 보고서(/tmp)는 세션을 넘지 못한다.** BW 조사에서 첨부로 지정한
  report_de_batch2.md 가 파일시스템에 없었다(ls 실패). holiday_14 §서두의
  "다음 세션 첨부는 각각 필요하다" 전제가 실측으로 반증됐다. 한 건의 부재로
  끝날 일이 아니었다 — 작성 시점 전수 확인 결과, 레포(rules/·docs/·tests/)가
  이름으로 참조하는 /tmp 보고서 **11개 전부**가 없다(실재 0개). 이 세션 여섯
  벌 중 넷도 이미 사라졌다. 이후 NI·RP 프롬프트는 첨부 없는 전제로 작성했고,
  독립 실측 규약이 공백을 메웠다.
- **"셋·다섯 줄 규칙"의 소생과 항목 수가 8세션 동안 표류했다.** 이전 작업의
  1단계 실측에서 드러났다. 다섯 줄 규칙은 holiday_08 §6 이 만든 것이고
  holiday_08 이 스스로 "이번 세션이 하나를 더했다" 라고 적었는데, holiday_09
  부터 "Holiday_07 §7 의 셋과 다섯 줄 규칙" 으로 묶이면서 07 §7 소생으로
  귀속됐다 — holiday_07 §7 에 다섯 줄 규칙은 없다. 항목 수도 §7 "셋 다" →
  §6 "넷 다" → holiday_09 수 언급 소멸 → holiday_12 "셋·다섯 줄" 압축으로
  읽히지 않게 됐다(지금 문면은 "셋 또는 다섯 줄" 로도 읽힌다). 내용 자체는
  표류하지 않았다. 문서 간 전파 오류의 세 번째 사례다 — holiday_12 "13건",
  holiday_14 "피드별 로그 원복" 에 이어. 이전 작업 안에서 한 번 더 재현됐다 —
  2단계 지시문이 원문의 "커밋 oneline" 을 둘로 읽어 다섯을 여섯으로 셌고
  (holiday_12 §1 "기존 여섯 줄" 오기와 같은 형태), 닫힌 결정("문면은 원문
  그대로")이 원문인 다섯을 채택하게 했다. 이전(§6)이 그 표류를 닫는다.
- **#59 는 신규 피드를 자동 노출하지 않는다.** 세션 내내 "랜딩은 #59 가
  자동으로 흡수한다"를 가설로 두고 확장 네 PR 에서 index.html 을 미뤘으나,
  실체는 index.html 안 수기 JSON 블록이었다. 확장 네 PR 은 index.html 을
  한 줄도 건드리지 않았고, 그것을 잡는 테스트가 #59 안에 있어 넷 다 조용히
  CI 를 통과했다. 결과적으로 발행본 아홉 중 다섯만 노출되는 상태가 하루
  지속됐다. "랜딩은 후속 PR 몫" 결정 자체는 마크업 반복 방지 목적으로
  맞았으나, 노출 공백 비용을 과소평가했다.
- (부수) 지연 표본은 cron 세대별로 갈라야 한다. 변경 커밋 b83bf09
  (2026-09-07T08:56:20Z)보다 앞선 run 은 구 cron(`0 0 * * 1`) 표본이다 —
  09-07 run(236.70분)이 여기 해당한다. 전수 실측으로 닫았다: schedule run 은
  지금까지 **6건이 전부**이고, 구 cron 4건이 98.78 · 101.17 · 292.05 ·
  236.70분, 신 cron 2건이 123.83 · 111.23분이다. 신 cron 2건은 현재 구 cron
  범위 안쪽이다 — 오프셋 효과 판정은 하지 않는다. holiday_14 의 "schedule
  4/4회 98~292분" 은 구 cron 표본 서술로서 **맞다**(cron 활성화 2026-08-11
  이후 월요일 4회가 전부 발화했고 4회 모두 늦었다). 전 6건 startedAt ==
  createdAt — run 생성 지연이지 실행 지연이 아니다.
